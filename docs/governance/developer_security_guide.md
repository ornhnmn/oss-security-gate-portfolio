# 개발자 오픈소스 보안 가이드

| 대상 | 개발자 및 서비스 담당자 |
| 문서 상태 | Draft |

## 1. 가이드 목적

개발자가 오픈소스 사용 과정에서 발생하는
공급망 보안 위험을 이해하고
취약점을 직접 조치할 수 있도록 지원한다.

## 2. 신규 패키지 사용 전 확인사항

- 공식 배포처에서 제공되는 패키지인가?
- 패키지명과 버전을 정확히 확인하였는가?
- 사용 목적에 적합한가?
- 불필요한 의존성이 추가되지 않는가?
- 유지보수 및 보안 업데이트가 제공되는가?
- 라이선스 및 이용 조건을 확인하였는가?
- 알려진 취약점이 존재하는가?
- 필요한 반입 심사를 완료하였는가?

## 3. 안전한 의존성 관리

패키지 버전을 명시적으로 관리하고
승인되지 않은 변경을 제한한다.

직접 의존성뿐만 아니라
전이 의존성의 변경도 확인한다.

불필요한 빌드 및 개발 도구가
실제 실행 환경에 포함되지 않도록 관리한다.

버전 고정만으로 패키지 무결성이
보장되는 것은 아니므로 향후 해시 기반
검증 및 승인된 저장소 사용을 적용한다.

## 4. SCA와 SBOM의 차이

SCA는 소프트웨어 구성요소의 알려진
취약점 및 관련 위험을 분석하는 활동이다.

SBOM은 소프트웨어를 구성하는
패키지 및 구성요소의 목록이다.

SBOM은 취약점 대응과 구성요소 추적에
활용할 수 있으나 자체적으로 모든
보안 위험을 판정하는 것은 아니다.

## 5. Security Gate 실패 시 대응

1. GitHub Actions 실행 결과를 확인한다.
2. Security Gate 실패 원인을 확인한다.
3. 탐지된 패키지 및 취약점 식별자를 확인한다.
4. 수정 버전과 영향받는 버전을 검토한다.
5. 업데이트 또는 불필요한 패키지 제거를 수행한다.
6. 호환성 및 자동화 테스트를 수행한다.
7. SCA 재검사와 정책 평가 결과를 확인한다.

입력 데이터 검증 오류와 실제 취약점에 의한
정책 위반을 구분하여 대응한다.

## 6. 취약점 조치 사례

### Requests

HTTP 통신 라이브러리의 알려진 취약점에
대응하기 위해 패키지를 업데이트하였다.

TLS 인증서 검증을 비활성화하지 않도록
애플리케이션의 사용 방식도 검토한다.

### PyYAML

YAML 처리 라이브러리의 알려진 취약점에
대응하기 위해 패키지를 업데이트하였다.

일반적인 설정 데이터 처리에는
yaml.safe_load를 사용한다.

라이브러리 업데이트와 안전한 사용 방식은
상호 보완적인 보안 통제이다.

## 7. 취약점 예외 신청

즉각적인 조치가 어려운 경우
정해진 예외 승인 절차를 이용한다.

보안 정책을 임의로 수정하거나
검사 단계를 제거하여 우회하지 않는다.

예외 신청 시 대상 패키지, 버전,
취약점 식별자, 사유, 보완 통제 및
최종 조치 계획을 제출한다.

## 8. 비밀정보 관리

API 키, 인증 토큰, 비밀번호 및
개인 키를 소스코드에 포함하지 않는다.

환경 변수 또는 승인된 비밀정보 관리
체계를 이용한다.

.gitignore만으로 기존 Git 이력의
비밀정보가 제거되는 것은 아니다.

비밀정보 노출이 확인되면 해당 정보를
폐기 또는 교체하고 관련 이력을 점검한다.

## 9. 배포 전 확인사항

- [ ] 승인된 패키지 및 버전을 사용하였다.
- [ ] 자동화 테스트를 통과하였다.
- [ ] SCA 검사 제외 여부를 확인하였다.
- [ ] SBOM 정합성을 확인하였다.
- [ ] Security Gate 평가 결과를 확인하였다.
- [ ] 미해결 취약점과 예외 상태를 확인하였다.
- [ ] 라이선스 검토 상태를 확인하였다.
- [ ] 필요한 승인 절차를 완료하였다.

## 10. 핵심 원칙

취약점이 탐지되지 않는다는 사실만으로
소프트웨어의 안전성을 보장할 수 없다.

자동화된 검사와 사람의 위험 판단을
함께 적용하여 오픈소스 위험을 관리한다.

본 가이드는 개인 PoC의 운영 제안이며
실제 개발자 대상 교육을 수행한 기록은 아니다.
